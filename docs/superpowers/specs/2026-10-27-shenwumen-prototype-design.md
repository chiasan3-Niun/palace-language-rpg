# 神武門單關原型設計

## 目的

先完成《紫禁深宮·語文策》的第一個可玩的單關，確認學生能在清宮情境中理解並使用一項國文知識，而不是只猜選項。

原型關卡為第 01 關「神武門」：玩家扮演初入宮的秀女，必須完成名冊驗籍，辨認字形與六書線索，取得入宮資格。

## 目標

- 玩家能完成一輪可重玩的對話流程。
- 玩家至少完成一題六書／字形判斷題。
- 答題前能使用一次提示，並理解提示指向的判斷依據。
- 答對與答錯會產生不同的劇情回饋和狀態變化。
- 關卡結束時能看到一張可帶走的知識整理卡。
- 不看程式碼的人能在瀏覽器完成一輪，並說明自己為什麼答對或答錯。

## 非目標

- 本階段不製作其餘 11 關的完整內容。
- 不加入登入、雲端存檔、後端或帳號系統。
- 不加入隨機事件、派系關係、複雜分支或完整多結局。
- 不把「打倒皇上」作為本關玩法。
- 不在沒有教材或教師確認前，宣稱題目答案為正式教材答案。

## 已有素材與限制

- 場景使用 `public/images/backgrounds/BG_01_SHENWUMEN.png`。
- 若需要情境角色，優先使用既有角色立繪；第一版至少保留玩家立繪與神武門背景的替換介面。
- UI 使用既有 `UI_DIALOGUE_FRAME.svg`、`UI_CHOICE_BUTTON.svg`、`UI_HINT_BUTTON.svg`、`UI_HP_BAR.svg`、`UI_MP_BAR.svg`。
- 目前技術方向是瀏覽器可直接開啟的前端原型，採多檔案結構，不依賴後端。
- 第一版提示採兩層：語意點醒不扣才情值；排除陷阱扣少量才情值。第三層微課錦囊保留到內容穩定後。

## 核心流程

```text
開場 → 神武門報到 → 宮門官盤問 → 閱讀名冊／字形線索
→ 選擇回應 → 六書判斷題 → 即時回饋
→ 狀態更新 → 成功／重試 → 知識整理卡
```

### 1. 開場

顯示神武門背景、關卡名稱、任務目標與初始狀態：

- 容止值：100／100
- 才情值：0／100
- 本關提示：可使用

不在開場加入複雜世界觀說明。玩家先知道自己要完成「名冊驗籍」即可。

### 2. 情境對話

宮門官指出名冊中有一個字的字形或構造可疑，要求玩家說明判斷方式。玩家先選擇禮貌回應，再進入語文判斷。

第一版只保留一個主要劇情分歧：

- 合宜回應：進入題目，容止值不變。
- 失禮或逃避回應：容止值下降，仍可進入題目，讓玩家能重試而不是立刻結束。

### 3. 六書／字形判斷題

題目採單題選擇，不先做拖曳合成。題目資料至少包含：

- 題幹
- 選項
- 正確答案欄位
- 判斷依據
- 答錯回饋
- 答對回饋
- 教材或教師審查來源
- `status`: `placeholder` 或 `reviewed`

在教材來源確認前，正式題目不得標成 `reviewed`。原型可以使用明確標示的佔位題測試互動流程。

### 4. 提示

- 「語意點醒」：指出玩家應觀察字形、構件或造字意義，不扣才情值。
- 「排除陷阱」：移除一個錯誤選項，才情值扣 10 點，每題最多使用一次。

提示使用後要立即顯示文字回饋，讓玩家知道提示改變了什麼；不能只把選項靜默刪除。

### 5. 結果

答對：

- 才情值增加 10 點，最高 100。
- 顯示正確原因。
- 解鎖「神武門驗籍」完成標記。
- 進入知識整理卡。

答錯：

- 容止值下降 15 點。
- 顯示錯誤原因與重新閱讀方向。
- 保留「重新判斷」按鈕。

容止值降至 0：顯示本關失敗畫面，文案使用「任務失敗，重新推理」；不呈現賜死、刑罰或暴力畫面。

```text
┌──────────────────────────────┐
│ 場景背景                 狀態列 │
│                              │
│      角色立繪／情境文字         │
│                              │
├──────────────────────────────┤
│ 對話框                         │
│                              │

│ [語意點醒] [排除陷阱]          │
```

文字必須覆蓋在可讀性足夠的對話框內；背景圖片不能直接承擔重要文字。桌面與行動裝置都要能閱讀題幹、選項和回饋。

關卡資料維持可替換格式：

```js
  dialogue: [],
  question: {
    status: "placeholder",
    prompt: "待教材確認的六書／字形判斷題",
    options: [],
    answer: null,
```

核心 UI 不應把題目文字、答案或回饋寫死在畫面程式中；新增或替換題目時，只修改關卡資料。

## 驗證方式

1. 結構檢查：關卡資料包含目標、場景、題目、答案狀態、回饋與失敗條件。
2. 流程檢查：可以從開場走到成功、答錯後重試、容止值歸零三條路徑。
3. 教學檢查：答對回饋說明原因；答錯回饋指向下一次閱讀方法；提示不取代判斷。
4. 素材檢查：神武門背景、角色立繪、對話框、選項按鈕、提示按鈕與狀態列能正確載入。
5. 使用者檢查：邀請一位不看程式碼的測試者完成一輪，請他說出答題理由；若只能說「因為系統判定」，原型不算通過。

## 待確認事項

- 第一關題目來源決定採「專案自編、教師可審查」：先依國中國文共通的六書與字形概念編寫原型題目，再補上教師審查與教材對照資料；在審查完成前維持 `placeholder` 或 `pending-review`，不得標為正式答案。
- 角色名稱是否沿用現有清宮／影視角色，或改成原創角色。
- 「初入宮秀女」的玩家稱呼、身分與語氣是否要固定。
- 題目通過教師審查後，是否需要保留完整來源、頁碼與審查者欄位。

## Approaches

### A. 單題選擇原型（本設計採用）

先用一題完成對話、答題、提示、狀態與回饋的完整閉環。優點是最容易驗證教學效果，也符合目前專案路線圖；缺點是尚未呈現原計劃中的拖曳造字。

### B. 拖曳造字原型

直接把部件拖入字形槽位，讓玩家完成六書判斷。優點是互動更貼近原始計劃；缺點是會同時增加拖曳操作、行動裝置支援與錯誤回饋的複雜度，尚未能確認題目內容是否適合這種操作。

### C. 十二關資料骨架

先建立所有關卡資料與地圖入口，再填神武門。優點是早期可看見完整產品輪廓；缺點是會延後第一關的教學驗證，且目前多數關卡的答案來源尚未定案。

本設計選擇 A，因為它最符合「先完成一個可重玩的單關，確認學生真的會使用語文知識」的既有專案目標。
